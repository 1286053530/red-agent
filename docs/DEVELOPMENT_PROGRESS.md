# 筱竹书瑾开发进度

更新日期：2026-10-25（北京时间）

当前发布版本：**2.1.19**

功能与验证基线：[28933ac](https://github.com/1286053530/red-agent/commit/28933ac73b5a96ce03245468d450666ad008c3e9)

本文区分“已经实现”“已有基础、仍需增强”和“尚未实现”。后续优先级是建议的开发顺序，不代表已经排定工期或承诺上线时间，不使用缺乏依据的完成百分比。

## 一、当前阶段

项目已经具备可安装、可下载的本地开发 Agent 工作台：导入项目、连接模型、分析源码、提出修改、审核执行、验证交付，并保存任务记录。

当前架构为 **Electron 桌面端 + 原生 Web 前端 + Python/FastAPI 后端**。每个任务由单 Agent 完成工具反馈循环，配合计划管理、基础开发规范和内置 Skill；尚未实现多 Agent 协作或图工作流引擎。

下一阶段重点是补齐 **Python 项目验证、增量修改、上下文恢复和真实模型评测**。小红书定位为等待任务时的手动浏览入口，不作为自动采集业务继续开发。

## 三、已有基础，但还需要增强的能力

| 能力 | 当前已经具备 | 仍存在的限制 |
| --- | --- | --- |
| Python 项目开发 | Python 后端已经完成，Agent 可以阅读 Python 源码并提出修改 | Agent 执行器尚不能直接运行 Python/pytest；不能把后端使用 Python 等同于已具备 Python 项目验证闭环 |
| 大文件处理 | 审查读取已支持大文件与分页 | 整文件替换仍限 160 KB；还没有面向大文件的局部补丁编辑工具 |
| 差异与修改恢复 | 有变更审核、真实 unified diff、冲突保护和单项恢复 | 差异超过展示上限不能标为复核成功；尚未提供完整的多文件事务回滚和独立 Git 快照方案 |
| 项目过滤 | 有统一内置排除表和不可越过的敏感路径限制 | 尚未解析项目 `.gitignore`，也没有可视化的用户自定义包含/排除规则 |
| 上下文与断点续作 | 已保存计划、工具历史、读取范围及任务结果；支持人工继续 | 历史主要按字符预算裁剪，尚无完善的自动证据摘要、跨任务记忆和长任务上下文重建策略 |
| 权限与安全 | 已区分只读、逐项审核、按任务自动执行，并在后端检查 | 命令白名单不是操作系统沙箱，获准的项目检查仍能执行本机代码；尚无进程/网络资源的完整隔离 |
| 任务完成质量 | 已有验收门槛、失败分类、防循环和确定性回归 | 尚未形成真实模型、真实项目的固定任务基准；不能据此承诺任意模型的完成率 |
| Skill 使用 | 已有一个软件开发 Skill，包含按需加载的补充指引 | 尚未实现多个独立 Skill 的自动路由、注册管理和基于评测的选用策略 |
| 下载与升级 | 已提供公网 HTTP 下载、版本化文件与校验清单 | 尚未配置 HTTPS、Windows 安装包签名或客户端自动更新 |

## 四、建议继续开发的事项与验收标准

### P0：优先形成可靠的开发闭环

| 事项 | 需要实现的内容 | 建议验收标准 |
| --- | --- | --- |
| Python 检查支持 | 在现有权限、超时、日志和完成门槛内接入 Python/pytest；识别项目环境与允许执行的参数 | 真实临时 Python 项目先出现测试失败，再由 Agent 修复并通过；无测试、执行中和失败结果均不能标为完成 |
| 局部补丁编辑 | 支持按已读取的上下文修改局部内容，校验当前版本，展示修改差异，避免整份文件替换 | 超过 160 KB 的文件可局部修改、审核、验证和恢复；上下文不匹配或外部已修改时拒绝覆盖 |
| 真实任务评测 | 固定一组代码审查、缺陷修复、小功能开发、大项目定位和失败恢复任务，明确模型及执行条件 | 每次评测保留目标、代码基线、结论、实际检查、人工介入、耗时和 Token；形成可复核报告，再决定是否调整防循环阈值 |

### P1：增强长期使用的稳定性与可控性

| 事项 | 需要实现的内容 | 建议验收标准 |
| --- | --- | --- |
| 上下文摘要与恢复 | 将关键证据、文件范围、未完成事项和验证结果整理为结构化摘要；继续时重新核对变化 | 长任务中断或历史裁剪后，可恢复原目标、明确已知/未知结果并继续；文件变化会使旧证据失效 |
| 多文件变更保护 | 增加任务变更清单、检查点和成组恢复；保护开始任务前已有的用户修改 | 回退只影响本任务改动，保留用户未提交修改；部分恢复失败会明确报告，不伪称全部成功 |
| 可配置项目过滤 | 支持 `.gitignore` 和额外包含/排除配置，同时保留敏感路径等硬边界 | 大仓库读取及搜索一致遵守规则，用户能识别排除原因；配置不能开放凭据或项目外目录 |
| 执行隔离 | 设计可选的独立执行环境与明确的目录、联网、资源限制 | 未授权的目录或网络操作被执行层阻止，而不是仅靠模型指引；停止、超时和授权回归继续通过 |
| 发布与更新 | 补齐域名/HTTPS、签名及更新方案；更新前校验包、提示版本并保留失败恢复路径 | 下载可验证来源和完整性；更新失败仍可启动旧版本，用户可控制更新时机 |

### P2：在基础能力与评测稳定后再评估

| 方向 | 评估重点 |
| --- | --- |
| 多 Skill 路由 | 先区分审查、修复、功能开发等任务，验证路由准确性和上下文成本，再扩展 Skill 数量 |
| 独立审查 Agent | 小范围比较“执行后独立审查”与当前单 Agent 的发现质量、成本和延迟，再决定是否引入多 Agent |
| 图工作流与任务调度 | 先确定真正需要分支、重试、并行和人工节点的场景，再设计编排，避免只为架构升级而重构 |
| 其他语言与平台 | 根据实际项目需求扩展执行器和安装包，逐一建立行为验证与平台回归，不默认现有 Node 方案通用 |

以上事项尚未全部实现；本文件只记录建议，不表示已经启动开发。强化学习训练目前不列为前置条件，先积累真实任务与评测数据。

## 五、明确不纳入当前功能计划的内容

- 小红书自动登录检测、二维码提取、内容采集、私信/通知同步和自动操作保持停用，不作为“待补齐功能”。
- 不以绕过官网限制为目标；内嵌页面由用户手动使用，官网自身的登录与风控规则仍然适用。
- 现阶段不扩展内容推荐、监测任务、收藏或策略简报等旧产品菜单，保持 Agent 为核心。
