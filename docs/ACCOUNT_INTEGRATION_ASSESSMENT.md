# 小红书账号接入重新评估

> 2.0.2 增加手动内嵌官网浏览，详见 [访问说明](MANUAL_EMBEDDED_ACCESS.md)。它只提供官网页面操作入口，不增加本文评估中的消息同步或授权能力。

评估日期：2026-10-24（北京时间）。适用项目版本：2.0.1。

用户确认的账号类型：普通个人账号。优先目标：集中查看和处理私信、通知。

## 结论

目前检索到的公开官方文档，不能确认存在向普通个人账号开放的通用私信收取、历史同步、发送回复及完整站内通知接口。因此不应承诺通过扫码或账号授权，就能把个人消息完整同步到工作台。继续保持 2.0.1 对自动浏览、DOM 采集、Cookie 接管和旧采集接口的停用状态。

官方账号授权可以用来识别用户身份，但公开权限不支持当前消息需求。工作台目前无需为身份展示增加授权流程；应在消息能力得到平台确认后再决定接入。

## 官方证据及边界

| 能力 | 查证结果 | 对本项目的含义 |
| --- | --- | --- |
| 账号身份授权 | 官方 Scope 文档当前开放 basic_info，主要为昵称、头像等基础资料；其他列出的权限仍标为规划中 | 不能把获得登录授权解释成获得私信、通知或推荐流权限 |
| 官方扫码授权 | Web/车机设备授权由官方签发授权信息并按规定流程取得 Token；其他终端形态需平台评估 | 官方授权二维码与从普通网页登录页面提取二维码是两种不同机制；桌面场景仍需确认资格 |
| 私信 API | 商业开放平台首页列有私信 API 与会话服务能力 | 可作为商业业务的接入候选，但尚未确认普通个人号的准入、历史范围、读写权限、通知覆盖和回调方式 |
| 小程序客服消息 | 官方小程序文档描述的是用户与小程序商家的客服会话和相应回复能力 | 不能当作读取普通个人账号全部私信的接口 |
| 点赞、收藏、评论、关注、系统通知 | 本次没有找到能够证明面向普通个人号开放完整通知聚合能力的官方文档 | 与私信分开核实，不能把商业会话权限延伸到全部站内通知 |

证据不足表示当前不具备立项依据，不等同于断言平台永远不会提供这些能力。没有登录用户账号、访问私信、申请凭据或向平台提交咨询。

## 可行方案

### 普通个人号当前方案

官方 App 或系统浏览器负责查看和发送消息。工作台可提供用户主动粘贴文字、上传截图后的消息整理、搜索、标签、待办、摘要与回复草稿；最终由用户在官方页面确认发送。

这属于消息辅助处理，无法提供实时同步、全量历史、可靠未读数、官方已读状态或直接发送。导入内容可能包含他人隐私；默认本机保存，若要发送给模型服务，应在发送前明确告知并允许用户选择。

以上为建议设计，当前 2.0.1 尚未实现消息导入和回复草稿功能，本次评估没有新增采集或授权代码。

### 确实需要自动消息聚合时

先通过官方渠道确认账号和应用资格，以及具体消息产品。至少要获得以下信息，再决定开发：

1. 是否支持当前普通个人账号，而非仅指定商业账号或客服场景。
2. 是否分别支持消息读取、历史会话、消息推送、回复发送，以及各类通知。
3. 授权范围、调用限额、历史回溯范围、撤销机制与错误处理要求。
4. 桌面应用的授权方式、服务端部署要求和凭据保管方式。

如用户确有企业经营场景，可另行评估商业私信 API；账号升级本身不代表一定获得 API，更不代表可以读取全部个人消息和系统通知。不建议仅为绕过当前限制而升级账号或采购来源不明的接口。

### 获得官方批准后的架构建议

用户主动发起官方授权；Python 服务端只处理获批接口与权限。若产品支持消息事件推送，则使用其规定的回调机制，处理验签、幂等、撤销及限流；发送回复应有清晰的用户操作和发送结果。

需要统一 app_secret 的方案不应将其随 Electron/Python 安装包公开分发。本地 Python 服务不是保密的远程服务端；是否支持纯客户端授权必须由对应官方产品确认。没有消息权限时不得退回网页采集作为兜底。

官方授权流程中规定的短期授权状态轮询，与此前持续访问普通页面、读取消息的后台自动化不同；不能将两者简单等同。本项目目前不实现任何一个授权流程，待资格与实际业务权限确认后再设计。
