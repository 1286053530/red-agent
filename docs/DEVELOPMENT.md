## 1. 目标与范围

产品最初定位为偏商务风格的小红书内容工作台：登录自己的账号，在系统中查看推荐内容和消息。随后增加软件开发工作空间，支持导入本地项目、配置模型厂商，并将品牌由「观数」改为「筱竹书瑾」，提供 Windows 桌面客户端。

本轮的核心目标是让开发 Agent 形成可观察的闭环：

> 理解目标 → 按需获取上下文 → 执行动作 → 观察实际结果 → 验证与纠错 → 完成或请求帮助。

范围收敛到 JavaScript / Node 项目的修改与回归验证：单个支持工具调用的模型、代码搜索与读写、受控终端检查、验证循环和执行记录。先验证一类真实文件与进程任务，未引入多 Agent、MCP 或通用长期记忆。

## 2. 需求演进与实现

### 2.1 小红书登录：从独立浏览器到客户端内会话

网页版通过后台独立浏览器访问官网，与用户普通浏览器不是同一份登录会话。开发期间该方式出现过 `300012 / IP存在风险`，而用户在普通浏览器中可以登录；因此不能把后台浏览器失败解释为用户浏览器或整个网络均不可用。

桌面版改为 Electron 内的官方页面与持久化会话。工作台账号卡片展示官方二维码；过期可刷新，扫码后等待手机确认。需要额外验证时，在客户端内打开完整官网页面，完成后返回工作台。二维码卡片、官网页面和后续内容读取共用该客户端的会话，不导入其他浏览器 Cookie，也不绕过官方验证。

登录状态、推荐内容和消息读取保留明确的未登录判断；隔离样本用于验证恢复、清理、二维码状态和内容提取。真实官网二维码显示曾完成烟测，但真实账号手机确认后的推荐、私信仍需用户验证。

### 2.2 开发工作空间与模型接入

工作空间入口指向开发 Agent 页面，提供本地项目导入、源码预览、项目会话、模型设置、修改预览和执行记录。界面沿用商务工作台风格，区分演示数据与真实本机项目操作。

模型配置支持 OpenAI Chat Completions 兼容协议与 Anthropic Messages 协议。用户填写接口前缀、模型名称和 API Key；模型需支持工具调用。配置保存在本机，密钥使用 AES-256-GCM 加密，前端接口不返回原始密钥。任务上下文和按需读取的源码会发给所选模型服务，不能将「本机工作台」理解为离线模型执行。

### 2.3 从“提出修改”升级到“验证后完成”

原有读代码、生成修改、人工审核的流程补入持久化目标、验收标准、失败反馈、下一步与命令记录。系统通过 `finish_task` 控制完成状态，模型的自然语言“已完成”不能直接结束任务。

| 用户关切 | 实现方式 | 可检查结果 |
| --- | --- | --- |
| 模型看到正确上下文 | 搜索、分页读取、文件摘要、完整工具调用组压缩、独立任务检查点 | 修改前确认读取了文件当前完整版本；重启保留目标与事实 |
| 动作结果可信 | 命令 ID、实际退出、超时与停止处理、输出限制、重复执行保护 | 运行中不视为成功；中断结果未知，不自动重跑 |
| 什么时候算完成 | 当前源码行为测试、最终变更复核、带证据完成 | 旧测试、语法检查、待审核修改和未退出命令均不能直接完成 |
| 自主执行可控 | 默认逐项审核；本次任务可授权自动修改与检查 | 展示修改内容、命令与目的；冲突时拒绝覆盖并保留恢复内容 |
| 为什么失败 | JSONL 事件、界面轨迹、用量与耗时统计、日志导出 | 能区分模型请求、工具错误、命令失败、审核等待与中断 |

### 执行与恢复的关键约束

- 文件工具限制在导入项目内，排除常见敏感名称、依赖/生成目录和符号链接。已有文件完整替换前必须读完当前版本，写入前再次核对摘要，避免覆盖外部改动。
- 检查命令使用参数数组和 `shell:false`，支持 `node --test`、`node --check` 及有限的 npm 检查脚本；不提供任意 shell、安装、发布或删除工具。
- 进程退出后才记录最终状态；最长 120 秒，输出保留末尾 24,000 字符，超过 2 MB 时终止进程。停止会终止进程树，源码变化会使旧验证失效。
- 相同源码与参数的命令默认复用记录；失败或中断后明确指定命令 ID 才重试。重启将未确认结束的命令标为中断，不能凭旧运行状态恢复为成功。
- 写入前保存原内容与拟议内容，恢复时同样核对当前文件；新建文件不自动删除。每个项目只允许一个活跃任务，待审核工作也占用项目。
- 每次继续最多 60 轮模型请求、180 次工具调用；接近上限会提醒模型收敛，达到上限时保留进度并标记为可重试失败，由用户显式重试。

命令限制属于应用策略，**不是操作系统沙箱**。测试和 npm 脚本仍可执行项目代码；只应授权可信项目。本版没有实现容器隔离、全盘回滚或对任意项目脚本的安全证明。

## 4. 开发中遇到的问题与修正

### 4.1 空测试文件被误认为有效验证

全量回归发现：当前 Node 版本对仅含注释的测试文件也可能返回退出码 0，并报告一个通过的测试。只检测 `tests 0` 无法拦截；直接将“只有一个测试”判为无效，又误伤正常单用例，导致闭环与 UI 完成断言失败。

最终改为自定义 Node 测试报告器，读取结构化事件，排除只有文件本身成功的结果，记录实际通过的用例数。回归同时保留正常单用例与空文件案例。该检查针对内置 `node --test`；npm 的测试脚本仍需审查其实际含义与测试覆盖。

### 4.2 多字节输出截断

命令输出测试暴露了直接处理 Buffer 分片时 UTF-8 字符可能被拆开的情况。运行器改用流的 `setEncoding('utf8')` 解码，并用 `Buffer.byteLength` 计量输出大小。回归验证中文输出和输出截断，避免把不完整字节当成有效诊断文本。

### 4.3 开发环境与桌面运行环境不一致

Electron 终端可能继承 `ELECTRON_RUN_AS_NODE`，导致启动方式错误。桌面启动/验证前清除此变量；客户端内部调用 Node 检查时，由运行器按需要设置。npm 检查通过本机安装寻找 CLI，未找到时明确报错；内置 Node 检查不依赖用户额外安装 Node.js。

新增桌面运行器验证，并在构建后从 ASAR 内加载运行器与报告器，实际执行行为测试和空文件检测，避免仅凭源码模式通过就认定安装包可用。

### 4.4 构建下载与上传认证

首次客户端构建因 Electron 二进制下载失败而中断；使用镜像完成依赖下载后，重新构建并以构建进程退出码确认结果。失败的首次构建未作为交付证据。

GitHub 推送曾遇到 HTTPS 连接重置与账号认证等待。本地提交先保留，用户在官方凭据管理窗口完成认证后，推送成功，再用 `ls-remote` 核对远端 `main` 与本地完整提交号一致。文档不保存认证信息、代理凭据或账号会话。

核心测试 [agent-loop.test.mjs](../tests/agent-loop.test.mjs) 使用真实临时 Node 项目，按顺序完成：

1. 读取存在错误的加法实现与原有测试。
2. 第一次修改仍然错误，实际测试失败并返回退出码 1。
3. 模型样本收到失败输出后更新计划，再读取并修正源码。
4. 再次执行原测试，得到退出码 0。
5. 检查最终变更，提交带证据的完成结果。
6. 检查任务状态、磁盘文件与 JSONL 事件，确认成功不是仅来自模型文字。

测试使用确定性模型响应，文件和子进程实际执行。它验证状态机、错误反馈和工具可靠性，**不等同于真实厂商模型的任务完成率评测**。UI 测试曾在失败规则误伤及一次独立运行中超时；修正后单独复查，并以最终全量 20/20 通过作为验收记录。

## 7. 当前限制与后续验证方向

完成证据仍依赖测试本身的有效性，系统不能只凭退出码证明所有业务标准被覆盖。项目检查具有真实本机执行能力；内置文件访问限制不能替代系统隔离。记录包含工具输入输出和可能的源码，应按项目数据保管。

后续优先使用一组固定的真实 Node 修复任务、选定一个实际模型配置，记录任务是否完成、是否发生错误修改、人工介入次数、耗时和实际费用。现有界面已经提供 Token、耗时、失败检查与审核计数，但未完成真实模型的基准数据采集，未生成虚构的完成率或费用。

进一步扩展前，应先补齐真实账号扫码后的业务验收与真实模型任务评测，再根据证据决定是否需要更强隔离、更多语言、长期记忆、Skills、MCP 或多 Agent。
